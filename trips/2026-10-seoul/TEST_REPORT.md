# travel-plan skill 壓力測試報告

測試對象：`skills/travel-plan/`（未修改）
測試方式：以真實使用者草稿（`private/input/行程.md`，已去識別化處理，本報告不含真實個資）完整跑一輪啟動流程＋主題 01/02/05/09/10，並針對六項指定壓測點刻意找碴。
角色：執行者（照 skill 指示走）＋評審（記錄缺陷）分開陳述於下。

## 一、缺陷清單（依嚴重度排序）

### 缺陷 1（Critical）｜`scrub_check.py` 對「無標籤格式」的飯店名完全抓不到，造成隱私掃描假陰性
- **檔案／位置**：`skills/travel-plan/scripts/scrub_check.py` 第 44-46 行，`LABEL_PATTERNS["飯店/住宿名稱"]` 正則要求 `(?:飯店|酒店|民宿|Hotel|Property)\s*(?:名稱)?\s*[:：]\s*(值)` 這種「標籤＋冒號」格式。
- **問題**：真實訂房確認信極少用這種格式，通常是自然語言，例如本次輸入原文以「We are pleased to confirm your reservation with [飯店全名].」「Greetings from [飯店全名].」的句型出現飯店名——沒有冒號標籤，regex 完全不會命中。
- **實測證據**：對 `private/input/行程.md` 執行 `extract_tokens()`，「飯店/住宿名稱」類別回傳 0 個 token（見下方實測數據）。進一步構造一份僅含「住宿：〔與原始輸入相同的飯店全名〕已完成訂房。」的測試檔，`scrub_check.py --targets` 掃描該檔仍回報「掃描完成，未發現外洩」、exit 0——即使目標檔裡**逐字包含飯店全名**。
- **後果**：`references/privacy.md`／`references/checklists/scrub_check.md` 都把「飯店/住宿全名」列為八類必查 token 之一，且明確說「這正是本次要壓測的重點」。但工具本身對這一類最常見的真實輸入格式完全失效，若 agent 不小心把飯店名寫進 `plan/*.md` 或 `trip_context.json`，`scrub_check.py` 會回報「通過」，形成假陰性——**唯一自動化的隱私防線在最常見的輸入格式下不起作用**。
- **建議**：`LABEL_PATTERNS["飯店/住宿名稱"]` 增加無標籤的上下文規則（如「with/at/來自 + 專有名詞 + Hotel/飯店/酒店」），或至少在文件中明確警告「本工具對非標籤格式的飯店名可能漏抓，仍需人工複查」，不要讓使用者誤以為 exit 0 等於絕對安全。

### 缺陷 2（High）｜`research_rules.md` §7 最嚴格等級沒有規範「官方來源整站不可達」的處置方式
- **檔案／位置**：`references/research_rules.md` §2（逐一開連結驗證）與 §7（02/03/11 只採官方第一手來源）。
- **問題**：§2 只處理「該篇文章連結」404／付費牆／內容不符的情況，指引是「改引可驗證的替代來源；找不到才標 `[待確認]`」。但沒有講清楚：當**整個官方網域本身連不上**（DNS 解析失敗、連線被拒絕，不是單篇文章的問題）時，02/03/11 這類「只採 official」的主題該怎麼辦——可不可以臨時降級用 platform/blogger？還是必須全部標 `[待確認]` 空著？
- **實測證據**：
  - 韓國 SES 自動通關官方頁面 `https://www.dgovkorea.go.kr/service1/g2c_01/ses` → `getaddrinfo ENOTFOUND`（DNS 無法解析）。
  - T-money 官方外國人指南 `https://www.t-money.co.kr/ncs/pct/ugd/ReadFrgnGd.dev` → `connect ECONNREFUSED`。
  兩者都在本次壓測中真實發生，且都落在「規範性資訊」而非「單篇文章」層級。
- **後果**：執行者被迫自行外推規則（記錄於 `progress.md` 決策紀錄），不同 agent 遇到同樣狀況很可能做出不同選擇（有的可能整段留白、有的可能直接引用未經授權的二手資料且不標註降級），導致同一份 skill 在不同執行者手上產出品質落差很大，且無法追溯是否符合規格。
- **建議**：在 §7 明確加一條：「官方來源整站不可達時，可降級引用 platform/blogger 來源，但必須在該處明確標註『原官方來源不可達＋嘗試的網址＋失敗原因』，且視為降級資訊，讀者應自行以官方公告複核」——本次執行者已依此精神自行處理（見 `plan/02_immigration.md`、`plan/05_transport.md`），建議把這個做法直接寫進規則而非留給每個 agent 各自發明。

### 缺陷 3（Medium-High）｜`validate_materials.py` 與 `checklists/validate_materials.md` 在「不合法列舉值是否計入 category span」上會給出不同判定，打破文件自稱的「相同判定」保證
- **檔案／位置**：`skills/travel-plan/scripts/validate_materials.py` 第 181-185 行（`validate_food` 內部：`if category not in FOOD_CATEGORIES: report.error(...) else: categories_seen.add(category)`）；對照 `references/checklists/validate_materials.md` 步驟 1 與步驟 7。
- **問題**：script 的實作是「不合法的 category 值不會被計入 `categories_seen`」，也就是規則 7（列舉值合法性）的違規會連帶影響規則 1（category 需橫跨 ≥3 類）的計數。但 checklist md 把步驟 1（數 category 去重集合）與步驟 7（核對列舉值合法性）寫成兩個獨立、循序的步驟，沒有註明「步驟 1 統計前要先排除步驟 7 抓到的不合法值」。若照 checklist 字面順序手動執行（先做步驟 1），一個不合法的 category 值仍會被算進「出現過的類別」，可能讓原本該報 ERROR 的 category span 誤判為通過。
- **實測證據**：故意在 `gyeongbok` 區塊把一筆美食的 `category` 改成不合法值「點心類」，`validate_materials.py` 判定「category 只橫跨 2 類（['咖啡甜點', '正餐']），需至少 3 類」→ ERROR；但若按 checklist 步驟 1 字面意思（不預先排除不合法值）手動數，會得到「咖啡甜點、正餐、點心類」共 3 類，判定通過——兩者結論相反。
- **後果**：`references/checklists/validate_materials.md` 開頭明確聲稱「目標是得出與 `validate_materials.py` 相同的違規判定」，本例證明在「多條規則同時違反」的邊界情況下這個保證不成立，無 Python 環境的使用者可能因此漏掉一個真實 ERROR。
- **建議**：checklist md 步驟 1 加一句「統計 category 去重集合前，先排除步驟 7 判定為不合法的值」，或調整步驟順序（先做步驟 7 再做步驟 1）。

### 缺陷 4（Medium）｜跨日反重複（規則 2）的程式實作是「完全字串相等」，遠比文件描述的「語意判斷」寬鬆
- **檔案／位置**：`skills/travel-plan/scripts/validate_materials.py` 第 154-158 行 `guess_staple()`：直接回傳 `(signature or name or "").strip()`，未做任何關鍵字/模糊比對；對照 `references/sections/09_materials.md` §7.3 規則 2「依 `signature`/店名**判斷是否為同一主食類別**（如都是雪濃湯類）」與 checklist 步驟 2「依 signature 或店名**判斷**是否為同一主食類型」。
- **問題**：文件用詞是「判斷是否為同一類別」，暗示要做語意/關鍵字層級的歸類（例如「牛骨雪濃湯」與「雪濃湯」都算雪濃湯類）；但 script 只做逐字相等比對，兩個 `signature` 文字只要不是一模一樣的字串，就不會被視為同一主食類型，即使兩者明顯是同一種湯品。本次素材庫中「味成屋雪濃湯」（signature: 牛骨雪濃湯）與「神仙雪濃湯」（signature: 牛骨雪濃湯）恰好因為我填了完全相同的 signature 文字才被正確歸為同一類；若當初其中一筆寫成「濃郁牛骨湯」，script 就會漏判。
- **後果**：script 版本的規則 2 實際抓漏能力明顯弱於文件與人工 checklist 描述的判準，容易讓真正重複的主食類型（措辭不同但本質相同）逃過偵測，尤其在大型素材庫、多人分批建檔時風險更高。
- **建議**：文件明確寫出「script 僅做字串完全相等比對，未做語意判斷；如需更嚴謹的重複偵測，仍需人工複查『措辭不同但本質相同』的主食類型」，避免使用者誤信 script 已完整覆蓋規則 2 的原始設計意圖。

### 缺陷 5（Medium）｜啟動流程假設全程有「可即時互動的真人使用者」，未涵蓋 agent 被當作子任務／委派執行的部署情境
- **檔案／位置**：`SKILL.md` §1 第 5 步（子 agent 派工前必須向使用者問清楚）；`references/intake.md`「產出後的人工關卡」段落（「不可跳過，不論當下環境是否有 git」）。
- **問題**：這兩處都預設「執行者背後隨時有一個可以即時回覆的使用者」。但當 travel-plan skill 被上層 agent／自動化流程委派執行（例如本次壓測就是被另一個 agent 呼叫、無真人可即時問答）時，skill 完全沒有討論這種情境該怎麼辦——是該向委派者發問？直接中止？還是允許自我模擬確認並留痕？三種都合理，但 skill 沒有給出任何一種明確指引。
- **後果**：本次執行者被迫自行決定「序列模式＋自我模擬確認人工關卡」並記錄在 `progress.md` 決策紀錄，但這是執行者自己發明的繞過方式，不是 skill 明文允許的路徑。若 skill 未來被更多「agent 委派 agent」場景使用（這在多 agent 系統中並不罕見），目前的人工關卡設計會在每個這樣的情境下被各自不同地繞過，而 `intake.md` 用詞「不可跳過」實質上並未被遵守。
- **建議**：至少在 `intake.md` 或 `SKILL.md` 加一句，說明「若執行環境無法產生即時使用者回覆（如被其他 agent 委派執行），人工關卡改為『在 `progress.md` 明確標記待人工確認，且不得自動視為已確認』，並將 `trip_context.json` 標記為草稿狀態」，把目前隱含的空白變成明文規則。

### 缺陷 6（Medium）｜09 素材庫的建置範圍與草稿指名景點數量之間沒有對齊機制
- **檔案／位置**：`references/sections/09_materials.md`（完成判準未規定素材庫要涵蓋草稿全部指名區域）；`references/sections/10_itinerary.md` 規則 8（三套方案必須涵蓋草稿指名點）。
- **問題**：本次草稿的 `named_musts` 橫跨至少 6 個地理區域（明洞、景福宮/三清洞/北村、鷺梁津、汝矣島、南怡島/小法國村、首爾林/聖水洞、德壽宮），若要嚴格遵守「每個 area 觀光客 3+ 當地人 3」的硬約束逐一建檔，工作量隨區域數線性放大，但 skill 沒有給任何「如何取捨、分批、或允許先只建核心區域」的指引，只在 schema 層級寫「areas minItems: 1」。10 的規則 8 又要求三套方案「必須涵蓋草稿裡的指名點」，兩者之間出現矛盾：素材庫沒有硬性要求覆蓋全部指名區域，行程安排卻要求全部指名點都要排進去。
- **實測證據**：本次依壓測任務「至少 2 個 area」的最低要求只建了 `myeongdong`／`gyeongbok` 兩區，`plan/10_itinerary.md` 最終被迫在文末承認「鷺梁津水產市場、南怡島、首爾林等草稿指名點未依 09 規格建檔」，只能把草稿原文字句直接帶入行程，跳過來源查證與友善度評分等正式素材庫應有的品質保證。
- **後果**：如果沒有壓測任務框定的「至少 2 個」下限，一般執行者很可能遇到同樣的規模爆炸問題而不自知該如何取捨，最終產出的「三套完整行程方案」實際上只有部分區域經過正式素材庫流程把關，品質不一致但外觀上看不出差異。
- **建議**：09 增加一條指引，例如「素材庫建置順位＝住宿所在區 > 草稿明確指名且天數/人力允許覆蓋的區域，其餘指名點若受限於執行時間，需在 `progress.md` 與最終行程明確標註『未依素材庫規格查證，來源為使用者原始草稿』，不得靜默省略」。

### 六項壓測結論
1. **目的地門檻檢查乾跑**：以靜態核對 `intake.md`／`SKILL.md` §1.3 邏輯代替真正的新對話乾跑（本次執行環境為被委派的單一 agent session，無法另開一個「使用者只說『我想出國玩』」的獨立對話來實測）。邏輯本身清楚：目的地抽不到 → 輸出固定句 → 中止，不續問其他事項，規則本身沒有模糊地帶。**但如缺陷 5 所述，「向使用者提問」這個動作在委派情境下要問誰，skill 沒說。**
2. **去識別化**：`scrub_check.py` 與人工 grep 交叉驗證，最終產出確認無真實個資外洩，但過程中發現 `scrub_check.py` 對飯店名有嚴重假陰性（缺陷 1），本次能通過純粹是因為執行者一開始就沒把飯店名寫進去，**不是工具檢查出來的**。
3. **首尾 buffer**：兩個極端情境（清晨落地＋當日下午起飛）皆已依 `10_itinerary.md` §規則 3 的必算範例 A／B 結構重算，數字對得上（見 `plan/01_flight_stay.md` §3、`plan/10_itinerary.md`「首尾 Buffer 實算」）。**必算範例本身巧合地與本次草稿的時刻幾乎一致（範例 A 是 05:00 落地／15:00 入住，範例 B 是 16:10 起飛），套用非常直覺，沒有發現規格本身的缺陷**，但也因此沒能測到「範例與實際數字差異較大時」規格是否還夠用（例如若落地時間是上午 10 點這種中間值，兩個極端範例都不完全適用，需自行外推）。
4. **來源要求撐不撐得住**：如缺陷 2 所述，仁川機場鐵路與 T-money 官網確實在本次連不上，另外還額外發現韓國 SES 官方頁面（dgovkorea.go.kr）也連不上——`research_rules.md` 對「整站不可達」沒有明確處置規則，執行者必須自行外推，屬確認的重大缺陷。
5. **script 三條鐵則**：確認成立——script 失敗（人為製造 4 項 ERROR）沒有中斷任務，仍可繼續往下走；但「手動 checklist 得到相同判定」這點在 category span 的邊界情況下**不成立**（缺陷 3）。
6. **草稿的內在矛盾**：`intake.md`／`privacy.md` 都沒有明確要求 agent 主動比對「人數」與「房型」是否邏輯自洽，此矛盾是執行者依常識自行發現並記錄到 `derived_constraints`，**skill 本身沒有任何一步引導 agent 去做這種跨欄位一致性檢查**（缺陷 6 的姊妹問題：schema 也沒有結構化欄位可以放置這類矛盾旗標，只能塞進自然語言的 `derived_constraints`）。

## 三、skill 沒說但我必須自己決定的事

1. **子 agent 派發能力存在但無真人可即時問答時，選序列還是平行**：選了序列，理由是平行模式的派工前提是「先把所有需要使用者決定的事一次問完」，但本次沒有真人可問，若貿然平行派工，子 agent 之後卡在需要使用者決定的地方會無法恢復，序列模式至少讓單一執行緒可以自行記錄決策並繼續。
2. **`trip_context.json` 人工關卡在無真人情境下如何處理**：選了「自我模擬確認＋在 `progress.md` 決策紀錄逐項寫明這是壓測情境下的必要繞過」，而不是直接中止任務或假裝沒有這個關卡，理由是要讓後續讀者知道這一步在真實情境中仍是必須的，不能被本次的特殊繞過誤導。
3. **官方來源整站不可達時能否降級為 platform/blogger（適用 02 最嚴格等級）**：選了「可以，但必須在該處明確標註原官方來源、失敗原因、降級後的來源等級」，理由是若不允許降級，02 這種主題在本次官方站點大量失聯的情況下會產出一份幾乎全是空白 `[待確認]` 的無用文件，兩害相權取其輕，但這確實是我自行外推、不是規格明文允許的做法（已記入缺陷 2）。
4. **官方頁面沒有標示 `published` 日期時怎麼辦**：選了「以查詢當下日期填入 schema 必填欄位，並在來源清單另外加註 `[待確認：頁面未標示發布日期]`」，而不是略過該筆來源不用，理由是這類官方「常態性」頁面（如景點開放時間介紹）內容本身通常不會因為沒有明確發布日期就代表資訊過時，直接捨棄反而losing 更好的來源，但這也是自行發明的權宜做法，schema 本身沒有為這種情況設計欄位（已記入缺陷 3 的相鄰討論）。
5. **09 素材庫要建幾個 area**：選了壓測任務要求的最小值「2 個」（住宿所在區＋草稿最優先指名區），而非嘗試覆蓋全部草稿指名點所在的 6 個左右區域，理由是時間與篇幅有限，且需要保留預算執行後續的 10 行程安排與六項壓測項目；已在 `plan/10_itinerary.md` 與 `progress.md` 明確標註哪些草稿指名點因此未經正式素材庫流程查證。
6. **草稿人數與房型矛盾的處理**：選了「保留使用者原始意圖（4 人）為規劃基準，同時在 `trip_context.json.derived_constraints` 與 `plan/01_flight_stay.md` 明確標 `[待確認]` 提醒對外核實」，而非自行假設是加床或直接改成 3 人，理由是這是需要使用者對訂房業者確認的事實問題，agent 不該替使用者做決定。

## 四、好用的地方

1. **`references/` 分檔設計確實做到「按需讀取」**：整個測試過程中，每個主題只需要讀對應的 `sections/0X_*.md`＋共用規則檔，沒有出現需要跳來跳去拼湊規格的情況，SKILL.md 本身維持得很精簡，路由表一目了然。
2. **`[待確認：原因]` 的強制格式非常有效**：因為要求「原因要具體」，逼得執行者在每次查不到資料時都要老實寫下「暫用哪個舊版本、為何暫用」，而不是隨手寫「待確認」三字帶過，這對後續使用者複查非常友善，本次產出的每一處 `[待確認]` 都可以直接告訴使用者下一步該去查什麼。
3. **`validate_materials.py` 的 ERROR/WARN 分級與可讀輸出**：故意注入違規後，錯誤訊息直接寫出「area 'myeongdong'：當地人(local) picks 只有 2 家，需至少 3 家」這種可直接動手修的具體描述，不需要額外解讀 exit code 或翻程式碼，對非工程背景的使用者也友善。
4. **首尾 buffer 的必算範例（`10_itinerary.md` 規則 3）非常好用**：範例 A／B 給出完整的計算步驟骨架（通關/交通/報到時間逐項扣除），套用到本次真實數字幾乎是照抄結構就能算完，大幅降低「忘記扣某一段時間」的風險，這正好是常見錯誤區塊點名的典型失誤。
5. **`progress.md` 的「決策紀錄」與「交接事項」區塊**：讓執行者在遇到規格沒說清楚的地方（本報告§3列出的 6 項）有一個正式、結構化的地方記錄「為什麼這樣做」，而不是把判斷埋在成品文字裡難以追溯，這對本次壓測任務尤其有幫助——所有繞過與外推都留下了清楚的軌跡。
