# 10｜行程安排

## 目的
把 `09_materials.md` 的素材組合成**三套**具體行程方案，以半天為單位呈現。本檔額外併入計畫書 §12.5「天氣與季節實況（含日出日落時間）」，因為天氣直接決定半天行程怎麼排，不另開新編號。

## 前置依賴
- **`09_materials.md` 與 `05_transport.md` 必須先完成**（Wave 3，依賴 Wave 2 的素材庫與 Wave 1 的交通資訊）
- `trip_context.json`：`dates`（含季節）、`arrival`/`departure`（首尾時刻，用於 buffer 計算）、`style`（風格偏好，若有）、`named_musts`/`named_undecided`（使用者指名景點）
- 若使用者提供既有行程草稿（`private/input/` 中），須先讀取並抽出草稿指名的景點清單

## 天氣與季節實況（§12.5，併入本檔）
產出時需含：
- 氣候常態值（該季節氣溫區間、降雨機率）。
- **日出日落時間**（依旅遊日期，直接影響半日行程怎麼排——例如日落 17:50 的話，觀景台/夜景行程就該提前排在該時段前後）。
- 當季限定活動（楓葉、慶典、花季等），若旅遊日期恰好涵蓋，應標註在對應的半天行程中。

此區資訊需檢索（依 `research_rules.md` 一般等級），優先 `tier: official`（氣象機關）取得氣候常態值與日出日落時間。

## §8 全部規則（逐條落實）

### 規則 1：半天為單位，不列具體時間
所有行程以「上午／下午」（必要時可拆「傍晚／夜間」）為區塊，**不寫死幾點幾分**（除首尾 buffer 段落依規則 3 需要具體算出可用時數外）。

### 規則 2：半天區塊內鄰近，日與日間可拉遠
- 同一半天內的景點與美食，彼此距離必須在**步行 15 分鐘或車程 10 分鐘內**。
- 不同天之間的區域可以有較大跨度（如 Day1 逛市中心、Day2 去郊區）。

### 規則 3：首尾強制 buffer

依 `01_flight_stay.md` 已算出的「最晚離開住宿時間」「抵達後最早可開始活動時間」，明確寫出「這個半天只剩 N 小時可用」，且**只排低風險行程**（不排需預約準時到場、體力消耗大、或移動距離遠的項目）。

**必算範例 A：清晨落地但 15:00 才能 check-in**
```
落地時刻：05:00（抵達機場）
+ 入境通關/行李提領/機場出關：約 60 分鐘 → 06:00 出關
+ 機場到市區交通：約 60 分鐘 → 07:00 抵達市區
= 07:00 起理論上人已在市區，但：
  - 住宿 15:00 才能 check-in，中間有 8 小時空窗
  - 旅客整夜未睡，體力低，即使時數長也不能排高強度行程
處理方式：
  1. 先去住宿或鄰近寄物櫃寄放大件行李（多數住宿可提前寄放，需查證是否需預約）
  2. 07:00-15:00 這個「加長版上午」只排低強度、可隨時中斯的項目：
     早餐、鄰近咖啡廳/室內歇腳（呼應 rainy_day_ok 素材）、短程散步景點
  3. 15:00 check-in 後才排當天真正的下午行程，且下午行程強度也要打折（旅客已醒 10+ 小時）
  4. 此半天在方案中標註：「Day1 上午：落地整理＋輕量歇腳（低強度，勿排需預約項目）」
```

**必算範例 B：回程日下午起飛**
```
起飛時刻：16:10
- 建議提前抵達機場時數：2.5-3 小時（依 01 查證的該機場國際線建議值）→ 最晚 13:30 需抵達機場
- 住宿到機場交通時間：假設 60 分鐘 → 最晚 12:30 需離開住宿
- 退房/收行李緩衝：30 分鐘 → 最晚 12:00 需完成退房
= 早上醒來到 12:00 之間，扣除早餐與退房，末半天實際可用約 3 小時
處理方式：
  1. 只安排住宿步行圈內的行程（不排需要往返交通的景點）
  2. 不排「不能寄不回來的行李」會牽涉到的行程（如需要大包小包才能進場的體驗活動）
  3. 若有退稅需求（呼應 07），需把退稅排隊時間也算進這 3 小時內
  4. 此半天在方案中標註：「Day5 上午：住宿圈內輕量活動＋退房＋前往機場（實際可用約 3 小時，不排新景點）」
```

兩個案例是**規格內必算範例**，agent 產出時須依實際 `trip_context` 數值重算，但計算步驟（拆解通關/交通/report 時間、寫出剩餘可用時數、只排低風險項目）必須沿用上述結構。

### 規則 4：層級呈現
每個半天行程必須依此層級展開：
```
大區域（呼應 09 的 area.name）
  └ 區域簡述（area.summary）
      └ 區域美食推薦（該區美食精選，非逐景點列出的重複清單）
          └ 區內景點（依 audience 與方案主軸挑選的 spots）
              └ 各景點旁步行可到的美食（food.near_spot 對應該景點的項目）
```

### 規則 5：三套方案
| 方案 | 適合誰 | 選材邏輯 |
|---|---|---|
| A｜經典必去 | 第一次去、想把地標都拍到的旅客 | 優先挑 `audience` 含 `tourist_must` 的景點 |
| B｜深度在地 | 已去過或想避開人潮、想體驗當地生活的旅客 | 優先挑 `audience` 含 `local_favorite` 的景點與 `food.audience: local` |
| C｜輕鬆慢遊 | 長輩/孩童同行、體力有限、不想趕行程的旅客 | 每天景點數**減半**、移動距離最短、`rainy_day_ok`／`室內歇腳` 密度最高 |

- 若 `trip_context.style` 有勾選風格，**第一套方案必須貼合該風格**（例如風格填「深度慢活」時，第一套需同時採 B/C 的選材邏輯，並在方案說明標註已依使用者風格調整）。
- 三套方案各自要在開頭明確寫出「適合誰」一句話。

### 規則 6：每半天配 1 個 Plan B
- 每個半天行程都要有 1 個從素材庫 `rainy_day_ok: true` 挑出的替代方案（下雨/公休/排隊過長時用）。
- Plan B 必須與該半天原行程地緣相近（同一 area 或步行可達），不能跳到別區。

### 規則 7：無指定風格與指名景點時，以部落客實際走過的路線優先
- 使用者未提供風格與指名景點時，**優先採用有部落客實際走過完整路線記錄的行程**（實際體驗過的動線比理論上鄰近但沒人走過的組合更不易出錯）。
- 此為 `tier: blogger` 來源在行程排序（而非單點景點推薦）上的特別用途，需在方案說明中註明依循哪篇實走路線。

### 規則 8：既有草稿優先串聯
- 使用者若已提供行程草稿（`private/input/`），**三套方案都必須涵蓋草稿裡的指名點**（`trip_context.named_musts`）。
- 三套方案的差異體現在「補洞」的部分——草稿沒明確決定的項目（`trip_context.named_undecided`），依各方案的選材邏輯（規則 5）填入不同選項，並在方案說明中列出「與草稿的差異點」。
- 若某指名點所在區域未依 `09_materials.md` §7.3 第 8 條建檔（素材庫沒有該區域），**該景點在行程中每次出現都要標註**（如「（未建檔，沿用草稿原文）」），不得原句照抄卻不註明——讀者要能一眼分辨哪些站是查證過的，哪些只是把使用者自己寫的話搬過來。禁止只在文末的「待確認」段落集中交代一次；那樣讀者讀到 Day2、Day3 的行程本文時，仍會誤以為每一站都經過同樣程度的查證。

## 必須回答的問題清單
- 抵達日與離境日的實際可用時數各是多少？依此排的行程強度合理嗎？
- 三套方案的差異看得出來嗎？還是選材幾乎一樣只是換了順序？
- 每個半天的 Plan B 是不是真的在同一區域、走過去到得了？
- 草稿裡指名的景點，三套方案是不是都排進去了？

## 檢索指引與來源要求
- 全部依 `references/research_rules.md`，一般等級。行程排序優先參考 `tier: blogger` 的實走路線（規則 7），景點/美食本身的來源已在 09 素材庫階段驗證，此處不重查，只做組合。

## 完成判準 checklist
- [ ] 三套方案皆以半天為單位、未列死時間
- [ ] 每個半天內景點/美食皆符合鄰近性（步行 15 分/車程 10 分內）
- [ ] 首尾 buffer 已依實際 `trip_context` 時刻重新計算，且只排低風險行程
- [ ] 層級呈現（大區域→簡述→美食→景點→景點旁美食）完整
- [ ] 三套方案各標「適合誰」，且若有風格偏好第一套已貼合
- [ ] 每半天皆有 1 個 Plan B，且與該半天同區
- [ ] 草稿指名景點三套方案皆涵蓋，差異點已列出

## 常見錯誤
- 首尾 buffer 只算「起飛時間 − 建議提前抵達時數」，忘記扣住宿到機場的交通時間與退房緩衝。
- 三套方案選材幾乎一樣，只是換了展示順序，沒有真正體現「經典必去/深度在地/輕鬆慢遊」的差異。
- Plan B 跳到別區的景點，實際下雨天根本走不過去。
- 忽略日出日落時間，把夜景行程排在天還沒黑的時段。
