# 10｜行程安排

## 目的
產出**三套**具體行程方案，以半天為單位呈現：1 套用 `09_materials.md` 的素材依使用者資訊客製（方案 A），2 套直接找真人走過的部落客行程節錄（方案 B/C，見規則 5）。本檔額外併入計畫書 §12.5「天氣與季節實況（含日出日落時間）」，因為天氣直接決定半天行程怎麼排，不另開新編號。

**本檔是參考草案，不是最終定案。** 這個 skill 真正的核心產出是 `materials/`——最新、正確、彼此距離關係清楚的景點/美食資料庫；`10_itinerary.md` 只是示範一種組合方式。使用者可以直接採用這裡的方案，也可以自己以半天為單位重組 `materials/` 的內容，或拿這份草案跟其他 agent 討論再深化。正因如此，本檔規則的檢索/驗證強度應該低於 `materials/` 本身——不必為了這份「草案」投入比素材庫更高的查證成本。

## 前置依賴
- **`09_materials.md` 與 `05_transport.md` 必須先完成**（Wave 3，依賴 Wave 2 的素材庫與 Wave 1 的交通資訊）
- `trip_context.json`：`dates`（含季節）、`arrival`/`departure`（首尾時刻，用於 buffer 計算）、`style`（風格偏好，若有）、`named_musts`/`named_undecided`（使用者指名景點）
- 若使用者提供既有行程草稿（`private/input/` 中），須先讀取並抽出草稿指名的景點清單

## 天氣與季節實況（§12.5，併入本檔）
產出時需含：
- 氣候常態值（該季節氣溫區間、降雨機率）。
- **日出日落時間**（依旅遊日期，直接影響半日行程怎麼排——例如日落 17:50 的話，觀景台/夜景行程就該提前排在該時段前後）。
- 當季限定活動（楓葉、慶典、花季等），若旅遊日期恰好涵蓋，應標註在對應的半天行程中。

此區資訊需檢索（依 `research_rules.md` 一般等級），優先 `tier: official`（氣象機關）取得氣候常態值與日出日落時間。

## §8 全部規則（逐條落實）

### 規則 1：半天為單位，不列具體時間
所有行程以「上午／下午」（必要時可拆「傍晚／夜間」）為區塊，**不寫死幾點幾分**（除首尾 buffer 段落依規則 3 需要具體算出可用時數外）。

### 規則 2：半天區塊內鄰近，日與日間可拉遠
- 同一半天內的景點與美食，彼此距離必須在**步行 15 分鐘或車程 10 分鐘內**。
- 不同天之間的區域可以有較大跨度（如 Day1 逛市中心、Day2 去郊區）。

### 規則 3：首尾強制 buffer

依 `01_flight_stay.md` 已算出的「最晚離開住宿時間」「抵達後最早可開始活動時間」，明確寫出「這個半天只剩 N 小時可用」，且**只排低風險行程**（不排需預約準時到場、體力消耗大、或移動距離遠的項目）。

**必算範例 A：清晨落地但 15:00 才能 check-in**
```
落地時刻：05:00（抵達機場）
+ 入境通關/行李提領/機場出關：約 60 分鐘 → 06:00 出關
+ 機場到市區交通：約 60 分鐘 → 07:00 抵達市區
= 07:00 起理論上人已在市區，但：
  - 住宿 15:00 才能 check-in，中間有 8 小時空窗
  - 旅客整夜未睡，體力低，即使時數長也不能排高強度行程
處理方式：
  1. 先去住宿或鄰近寄物櫃寄放大件行李（多數住宿可提前寄放，需查證是否需預約）
  2. 07:00-15:00 這個「加長版上午」只排低強度、可隨時中斯的項目：
     早餐、鄰近咖啡廳/室內歇腳（呼應 rainy_day_ok 素材）、短程散步景點
  3. 15:00 check-in 後才排當天真正的下午行程，且下午行程強度也要打折（旅客已醒 10+ 小時）
  4. 此半天在方案中標註：「Day1 上午：落地整理＋輕量歇腳（低強度，勿排需預約項目）」
```

**必算範例 B：回程日下午起飛**
```
起飛時刻：16:10
- 建議提前抵達機場時數：2.5-3 小時（依 01 查證的該機場國際線建議值）→ 最晚 13:30 需抵達機場
- 住宿到機場交通時間：假設 60 分鐘 → 最晚 12:30 需離開住宿
- 退房/收行李緩衝：30 分鐘 → 最晚 12:00 需完成退房
= 早上醒來到 12:00 之間，扣除早餐與退房，末半天實際可用約 3 小時
處理方式：
  1. 只安排住宿步行圈內的行程（不排需要往返交通的景點）
  2. 不排「不能寄不回來的行李」會牽涉到的行程（如需要大包小包才能進場的體驗活動）
  3. 若有退稅需求（呼應 07），需把退稅排隊時間也算進這 3 小時內
  4. 此半天在方案中標註：「Day5 上午：住宿圈內輕量活動＋退房＋前往機場（實際可用約 3 小時，不排新景點）」
```

兩個案例是**規格內必算範例**，agent 產出時須依實際 `trip_context` 數值重算，但計算步驟（拆解通關/交通/report 時間、寫出剩餘可用時數、只排低風險項目）必須沿用上述結構。

### 規則 4：層級呈現
每個半天行程必須依此層級展開：
```
大區域（呼應 09 的 area.name）
  └ 區域簡述（area.summary）
      └ 區域美食推薦（該區美食精選，非逐景點列出的重複清單）
          └ 區內景點（依 audience 與方案主軸挑選的 spots）
              └ 各景點旁步行可到的美食（food.near_spot 對應該景點的項目）
```

### 規則 5：三套方案——1 套客製 + 2 套部落客實走行程

三套方案**來源不同**，不是同一份素材庫拿去排列組合三次：

| 方案 | 來源 | 是否需涵蓋 `named_musts` |
|---|---|---|
| A｜依你的行程客製 | `09_materials.md` 素材庫 ＋ `trip_context`（`named_musts`／`derived_constraints`／`style`） | **必須**，見規則 8 |
| B、C｜部落客實走行程 | 上網找到的**完整、真人走過**的同目的地行程文章（見下方「B/C 的產生方式」） | 不強制，剛好路過算加分不強求 |

**方案 A** 沿用原本邏輯：依 `trip_context.style`（若有）決定選材傾向，`audience: tourist_must`／`local_favorite` 依風格加權，是唯一需要深度客製、逐條對照使用者資訊的方案。

**方案 B、C 的產生方式**（取代原本「深度在地／輕鬆慢遊」的選材邏輯描述；這是參考草案，強度刻意低於方案 A，不必比素材庫本身更昂貴）：
1. 依目的地與旅遊天數（如「首爾 5天4夜 行程」），檢索有逐日行程總覽的遊記（不是零散景點清單、不是廣告代購文）。找到 **1-2 篇**當骨架即可，不必湊滿多篇候選、不必逐篇比較挑選。
2. 開過連結確認文章真的存在、真的有逐日行程即可（§1/§2 一般等級查證），**不必**做到「多篇交叉驗證」的程度。
3. **不得自行拼裝或想像一份「像部落客會寫的」行程**——找不到合適的完整遊記時，直接說明「查無合適的完整行程文章」，改用方案 A 的素材延伸出一套差異化選材（例如全部改走 `local_favorite`，或景點數減半），**不能捏造一篇不存在的參考來源**。
4. **可行性調整（僅此一項需要客製）**：把原文行程對照 `trip_context.arrival`／`departure`／`stay.checkin` 等已保留在版控成品裡的時刻（見 `references/privacy.md`），只在時間對不上時調整（例如原文假設第一天可以整天玩，但使用者是紅眼班機需依規則 3 加 buffer），其餘天數與動線盡量保留原文骨架，不額外重新查證/增補景點與美食。
5. 方案開頭必須寫「本方案節錄自：《文章標題》- 作者/站名（連結）」，並註明做了哪些可行性調整、為什麼；若是步驟 3 的替代做法，改標「本方案為方案 A 素材的延伸選材（查無合適完整行程文章）」。這是這兩套方案跟方案 A 最大的差別，要讓使用者一眼看出「這是我的客製方案」還是「這是網路上找到的實走行程」。

- 若 `trip_context.style` 有勾選風格，只需要求方案 A 貼合該風格；方案 B/C 選材靠步驟 2 的檢索結果本身多樣，不再額外要求貼合風格。
- 三套方案各自要在開頭明確寫出「適合誰」一句話（方案 B/C 的「適合誰」就是原文作者設定的旅客類型，如「第一次去的小資族」）。

### 規則 6：每半天配 1 個 Plan B（僅方案 A 適用）
- 方案 A 的每個半天行程都要有 1 個從素材庫 `rainy_day_ok: true` 挑出的替代方案（下雨/公休/排隊過長時用），且必須與該半天原行程地緣相近（同一 area 或步行可達），不能跳到別區。
- 方案 B/C 是節錄自外部文章的完整行程（見規則 5），沒有對應的 09 素材庫可挑替代方案，**不強制**要有 Plan B；若原文行程剛好路過方案 A 已建檔的 area，可以順手引用該處的 `rainy_day_ok` 素材，找不到就在該半天註明「雨天/公休備案請彈性調整或參考原文其他建議」，不必為了湊 Plan B 另外查證新素材。

### 規則 7：（併入規則 5）
無指定風格與指名景點時，方案 B/C 本來就是找「部落客實際走過完整路線記錄的行程」，不再需要獨立規則——規則 5 步驟 1-3 已經是這個邏輯的具體做法。

### 規則 8：既有草稿優先串聯（僅方案 A 適用）
- 使用者若已提供行程草稿（`private/input/`），**方案 A 必須涵蓋草稿裡的指名點**（`trip_context.named_musts`）；方案 B/C 不強制涵蓋，原文行程剛好路過算加分，不必為了湊指名點去改寫原文。
- 方案 A 的差異體現在「補洞」的部分——草稿沒明確決定的項目（`trip_context.named_undecided`），依規則 5 的選材邏輯填入選項，並列出「與草稿的差異點」。
- 若某指名點所在區域未依 `09_materials.md` §7.3 第 8 條建檔（素材庫沒有該區域），**該景點在方案 A 行程中每次出現都要標註**（如「（未建檔，沿用草稿原文）」），不得原句照抄卻不註明——讀者要能一眼分辨哪些站是查證過的，哪些只是把使用者自己寫的話搬過來。禁止只在文末的「待確認」段落集中交代一次；那樣讀者讀到 Day2、Day3 的行程本文時，仍會誤以為每一站都經過同樣程度的查證。

## 必須回答的問題清單
- 抵達日與離境日的實際可用時數各是多少？方案 A 依此排的行程強度合理嗎？
- 方案 B、C 各自節錄自哪篇文章（或哪一個是方案 A 素材的延伸選材）？連結有沒有開過確認真的存在、真的有逐日行程？
- 方案 B、C 若都找到文章，是不是不同作者？（找不到第二篇合適文章時，其中一套改用方案 A 素材延伸是可接受的，不必硬凑兩篇不同來源。）
- 方案 A 的每個半天的 Plan B 是不是真的在同一區域、走過去到得了？
- 草稿裡指名的景點，方案 A 是不是都排進去了？

## 檢索指引與來源要求
- 方案 A：全部依 `references/research_rules.md`，一般等級，景點/美食本身的來源已在 09 素材庫階段驗證，此處不重查，只做組合。
- 方案 B、C：依規則 5，檢索「目的地＋天數＋行程/自由行」找 1-2 篇完整逐日遊記，開連結確認是真實存在的完整行程文章即可，不必逐篇比較挑選、不必多篇交叉驗證。

## 完成判準 checklist
- [ ] 方案 A 以半天為單位、未列死時間，每個半天內景點/美食皆符合鄰近性（步行 15 分/車程 10 分內）
- [ ] 首尾 buffer 已依實際 `trip_context` 時刻重新計算，且只排低風險行程（方案 A、B、C 皆適用）
- [ ] 方案 A 層級呈現（大區域→簡述→美食→景點→景點旁美食）完整
- [ ] 方案 A 涵蓋草稿指名景點，差異點已列出；方案 A 每半天皆有 1 個 Plan B，且與該半天同區
- [ ] 方案 B、C 各自附「節錄自：文章標題 - 作者/站名（連結）」或「延伸自方案 A 素材（查無合適完整行程文章）」
- [ ] 方案 B、C 若對原文行程做了可行性調整（時間對不上時），已寫明調整內容與原因

## 常見錯誤
- 首尾 buffer 只算「起飛時間 − 建議提前抵達時數」，忘記扣住宿到機場的交通時間與退房緩衝。
- 方案 B、C 其實是 agent 自己拼裝或想像出來的「像部落客會寫的」行程，沒有真正對應到一篇可驗證的原文，卻標成「節錄自」——這違反規則 5 步驟 3，查無合適文章要老實標「延伸自方案 A 素材」。
- 為了讓方案 B、C 也涵蓋草稿指名點，硬改寫原文行程塞進去——這違反規則 5「不強制涵蓋 named_musts」。
- Plan B（方案 A 的雨天備案）跳到別區的景點，實際下雨天根本走不過去。
- 忽略日出日落時間，把夜景行程排在天還沒黑的時段。
