# 檢索、引用與查證規範

> 本檔是所有主題規格（`references/sections/*.md`）共用的檢索與引用規則。各主題檔一律**引用本檔**，不重抄內容。
> 隱私相關規則見 `references/privacy.md`；進度與 commit 規則見 `references/progress_protocol.md`。

---

## 1. 深層連結規範

- 每個資訊點必須引用「實際參考的那一篇文章的完整深層網址（deep link）」，**不得是網站首頁或網域根目錄**。
- **自我檢查**：把網址去掉 `https://domain` 之後，剩下的路徑（path）不可為空。只有 domain（例如 `https://www.caa.gov.tw`）→ 判定不合格，必須重新檢索出實際文章網址。
- 連結文字必須含「文章標題 - 作者/站名」，格式固定為：
  ```
  [文章標題 - 作者/站名](深層網址)
  ```
  範例：`[大方推薦味成屋雪濃湯 - 樂活的大方](https://www.bring-you.info/korea/xxx)`
- **禁止自行拼湊路徑**：連結必須是 WebSearch／WebFetch 實際回傳的網址，不得憑經驗猜測 URL 結構、不得把不同頁面的路徑拼接。
- 官方機構資訊仍以第一手官網為準；部落客／攻略類必須深層到文章頁，不可引官網首頁代替。

## 2. 逐一開連結驗證

寫入任何連結前，必須**用 WebFetch 實際開啟**該連結，驗證以下三件事：

1. **回傳成功**：可正常讀取，非 404／付費牆／需登入。
2. **內容相符**：頁面實際內容與所引用的主題一致，不是掛羊頭賣狗肉的導流頁。
3. **是深層文章頁**：不是首頁、分類頁、搜尋結果頁或網域根目錄。

三項有任一項不通過：
- 優先改引可驗證的替代來源（官方或次佳來源）；
- 真的找不到替代，才在該處標記 `[待確認：連結無法驗證]`。
- **嚴禁保留未驗證的深層網址就直接寫入成品。**

## 2.4 雙邊官方來源：目的地國 ＋ 使用者所在國

**官方來源有兩邊，只查一邊就宣告「查不到」是不合格的。**

跨國旅遊的規範性資訊（簽證、電子旅行許可、自動通關、檢疫、免稅額度、領事協助）
幾乎都是**雙邊事務**：目的地國會公告一套，使用者所在國的主管機關與駐外館處也會公告一套，
而且後者通常**用使用者的母語寫、針對該國護照持有人、講得更具體**。

### 如何判定「使用者所在國」

依序取用，取到即停：

1. `trip_context` 明確記載的國籍／護照國別（若使用者說過）。
2. 由 `trip_context.origin.airport` 的 IATA 代碼推導所屬國家
   （`TPE`/`TSA`/`KHH` → 台灣；`NRT`/`HND`/`KIX` → 日本；`HKG` → 香港；`SIN` → 新加坡……）。
3. 都沒有 → 依使用者的**對話語言**推定，並在 `progress.md` 的「待覆核的推斷值」記一筆。

**這是變數不是常數**：使用者在台灣就用台灣的官方管道，在日本就用日本的，
不得把任何單一國家寫死在流程裡。

### 兩邊各要找什麼

| | 目的地國（例：韓國） | 使用者所在國（例：台灣／日本） |
|---|---|---|
| 主管機關 | 出入境管理機關、海關、檢疫、觀光主管機關 | 移民署／入國管理局、外交部（領事事務局）、衛福部／厚労省 |
| 駐外館處 | — | 我方駐目的地國的代表處／大使館官網（**最常被漏掉，卻最好用**） |
| 營運單位 | 機場公司、鐵路公司、交通卡發行商官網 | — |
| 語言 | 當地語言優先，英文次之 | 使用者母語 |

### 硬性要求

- 每一項規範性資訊，**至少要試過雙邊各一個官方入口**，兩邊都失敗才准進入 §2.5 的降級流程。
- §7 三個最嚴格主題（02 通關／03 保險／11 緊急）：宣告「官方不可達」前，
  必須在 `[待確認]` 裡**逐條列出兩邊各試了哪些網址、各自的失敗原因**，不得只寫「官方網站連不上」。
- 使用者所在國的官方頁面，`tier` 一律算 `official`，與目的地國官方同級。
- **語言不等於來源側**：目的地國的機關用使用者母語發布（例：駐日本的韓國大使館發日文公告），
  性質上仍是**目的地國側**，不能拿來充當使用者所在國側那一列。判定看的是「哪一國的機關」，不是「哪一種語言」。
- 使用者所在國側**確實找不到**時，要明寫「使用者所在國側查無官方來源」並列出試過的網址，
  **不得**用目的地國來源填進該欄位假裝雙邊都查過。

> **實跑教訓**：查「台灣旅客能否申辦韓國 SES 自動通關」，只往韓國官方網域鑽，
> 結果 `dgovkorea.go.kr` DNS 解析失敗，判定官方不可達、降級引部落格；
> 但同一件事我國移民署 `egate.immigration.gov.tw` 有完整中文官方說明頁。
> 同理「台灣是否豁免 K-ETA」，韓國外交部公告只點名 Canada 未列台灣，
> 而駐韓國台北代表部 `roc-taiwan.org` 直接寫明台灣豁免至 2026-12-31。
> **兩次都不是查不到，是只查了一半。**

## 2.5 官方站台整站不可達時的處置

§2 只規範「單篇文章抓不到」。實跑時遇過更麻煩的情況：**整個官方網域都連不上**
（實例：機場鐵路官網連續回 HTTP 500、交通卡官網 ECONNREFUSED、入境申報入口 DNS 查不到）。
最嚴格等級（§7）要求只採官方第一手來源，此時等於無路可走。
**進入本節之前，必須先完成 §2.4 的雙邊官方來源查找**——目的地國官網掛掉不等於官方來源不可達，
使用者所在國的主管機關與駐外館處仍是 `tier: official`。兩邊都試過才適用以下降級流程，**依序**嘗試：

1. **換路徑再試一次**：同網域的英文版／行動版／其他語系頁面，或該機構在其他官方網域的鏡像
   （例如觀光局官網、市政府英文入口）。成功就照常引用。
   **單一路徑 404 不等於整站不可達**：改用該站的站內搜尋、網站地圖或 WebSearch 加 `site:` 限定，
   找出真正的頁面路徑（§1 禁止自行拼湊 URL，所以只能用搜尋找、不能用猜的）。
   實跑教訓：`airportrailroad.com/customer/fare` 回 404 就放棄改引部落格，抄到錯誤票價；
   實際官方票價頁在 `/train/normal/fare`，一直都在。
1.5. **403 不等於不可達——換工具再試**：WebFetch 被 WAF／反爬蟲擋下（403、Cloudflare、Akamai）時，
   改用帶瀏覽器 User-Agent 的 `curl` 重試同一個網址：
   ```
   curl -sS -m 20 -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/131.0 Safari/537.36" "<url>"
   ```
   成功就照常引用（仍算 `official`），只是取得方式不同。
   實跑教訓：日本外務省 `anzen.mofa.go.jp` 對 WebFetch 回 403，同一網址 curl 帶 UA 回 **200**，
   內容逐字載明日本的 K-ETA 豁免期限；只憑 WebFetch 的 403 就判定「官方不可達」是誤判。
   **403 是「拒絕自動化客戶端」，不是「頁面不存在」**，兩者不可混為一談，`[待確認]` 也要如實區分。

2. **找官方的一手轉載**：政府新聞稿、機場官方公告 PDF、官方社群貼文。仍算 `tier: official`，
   但要在文中註明「原始頁面當時不可達，改引官方轉載」。
3. **前兩步都失敗 → 降級引用 + 附 Google 搜尋連結**，三件事缺一不可：
   - 引用兩個以上**互相佐證**、日期在時效內的 `platform`／`blogger` 來源；
   - 標記 `[待確認：官方來源 {網域} 當時不可達，本段改引 N 個非官方來源交叉佐證]`；
   - **附上一條 Google 搜尋連結**，讓讀者自己查到最新的官方說法：
     `[Google 搜尋：{關鍵字}](https://www.google.com/search?q={關鍵字經 URL 編碼})`
     關鍵字要能直接命中官方頁面，用「機構或設施官方名稱 + 要查的事項」，
     優先用當地語言（查韓國就用韓文、日本就用日文），必要時再補一組中文或英文。
     例：`https://www.google.com/search?q=%EA%B3%B5%ED%95%AD%EC%B2%A0%EB%8F%84+%EC%9A%94%EA%B8%88`

**不得**因為官方站台掛掉就略過該段落、或把非官方來源當成官方來源呈現。
Google 搜尋連結是**補救措施不是來源**，不能拿它取代 §1 要求的深層連結——每個事實仍要有自己的來源。

## 3. `[待確認：原因]` 註記規範

- 任何無法查詢到、不確定、或可能已過期的即時資訊，**嚴禁憑空編造（避免幻覺）**。
- 必須在該處清楚標示 `[待確認：原因]`，原因要具體（例如 `[待確認：2026 年最新時刻表官方尚未公告，暫引 2025 年版本]`），不得只寫「待確認」三字了事。
- 使用者可依此標記手動複查，因此原因描述要讓非本次執行的人也看得懂要查什麼。

## 4. 「留空即預設」哲學

- 使用者提供的資訊越少，agent 補的內容越通用（不做特殊化臆測），**但流程本身不可中斷**。
- 唯一硬停例外：目的地完全無法辨識（見 `SKILL.md` 的目的地門檻檢查）。
- 其餘欄位缺漏一律用合理預設值頂上，並在 `trip_context.json` 的 `inferred_fields` 與 `progress.md` 的「待覆核的推斷值」中標記，交由使用者事後確認，不因此暫停產出。

## 5. 來源分級 `tier`

每筆 `sources` 物件必須標註 `tier`，三選一：

| tier | 定義 | 適用場合 |
|---|---|---|
| `official` | 政府機關、法定主管機構、機場／航空公司／鐵路公司官網、駐外館處官網 | 通關、保險理賠條款依據、免稅門檻、緊急聯絡方式等第一手規範性資訊 |
| `platform` | 訂票／訂房／叫車／旅遊平台官方頁面（如 Klook、Trip.com、Kakao T 官網介紹頁），非個人部落格但也非政府機構 | 交通購票流程、App 功能說明、平台官方公告的優惠或限制 |
| `blogger` | 個人部落格、遊記、論壇（含 TripAdvisor、Dcard、Naver 部落格等使用者生成內容） | 景點/美食實際體驗、防雷細節、CP 值評比、當地人私房推薦 |

分級不是優劣排序，而是**依資訊性質選對應層級**：規範性、金額、法規類資訊優先找 `official`；體驗類、推薦類資訊 `blogger` 反而更可靠（見 §7 常見錯誤：官方網站通常不會告訴你哪家店好吃）。

## 6. `published` 日期欄位與時效規則

- 每筆 `sources` 物件必須有 `published`（文章／頁面發布或最後更新日期，格式 `YYYY-MM-DD`；只查得到年月則用 `YYYY-MM-01` 並在 `[待確認]` 註明精度不足）。
- **強制近一年**：`published` 距離「檢索當下日期」超過 1 年，該筆來源要標記 `[待確認：來源已超過 1 年，請覆核是否仍為最新]`，內容仍可採用但需標記。
- **真的找不到近一年來源**時，才可放寬到兩年內，但**必須在成品內文中明確註明「來源為 N 年前」**，不得靜默採用舊資訊。
- **超過兩年一律判不合格**，不得直接引用；需重新檢索或改標 `[待確認：查無近兩年資料]`。
- 此規則使「近一年最新資訊」這條要求變得可機械檢查（見 `scripts/validate_materials.py` 與其 md 後備）。

## 7. 風險分級：02 通關／03 保險／11 緊急

這三個主題「出事沒人能負責」，規格設為**全書最嚴格等級**：

1. **只採官方第一手來源**（`tier: official`）。部落格／論壇內容只能當作理解流程的輔助參考，**不得作為規範性結論的唯一依據**。
2. **每一條資訊後綴來源連結**，不得寫一段話只在段落末尾放一個籠統的參考清單——讀者要能對應到「這句話是哪個來源說的」。
3. **不接受概括引用**：禁止「根據官方網站」「查詢相關資料顯示」這類無法追溯的寫法，一律要有 §1 格式的深層連結。
4. 這三個主題的 `[待確認]` 標記必須**同時附上「暫用哪個舊版本」與「為何暫用」**，不能只寫查無資料就跳過。
5. **雙邊官方來源為硬性前提**（§2.4）：這三個主題的每一項結論，都必須先試過目的地國與使用者所在國
   各至少一個官方入口。宣告官方不可達時，`[待確認]` 需逐條列出兩邊各試了哪些網址與失敗原因。

## 8. 通用檢索策略（承襲舊 prompt）

- **官方機構自主關聯推導（雙邊）**：依目的地與目的機場，推導**目的地國**的官方主管機構（出入境管理處、機場官網、疾病管制／檢疫機關等）；
  同時依 `trip_context.origin` 推導**使用者所在國**的對應機關與駐目的地國館處（見 §2.4）。兩邊都算第一手官網，缺一邊即為查找未完成。
- **預設通用自主檢索**：使用者未指定來源偏好時，不限定國家或語言，檢索全球最熱門、高評價的頁面、遊記、論壇，取得客觀廣泛的資訊。
- **使用者來源偏好覆寫**：`trip_context` 若有來源偏好（如「優先台灣部落客」「優先 Klook 攻略」），須將偏好關鍵字納入搜尋（如加上 `台灣`、`部落客`，或 `site:` 限定），不得忽略此偏好。

## 9. 景點與美食的兩階段發掘管道（09 素材庫專用）

§8 的「通用檢索策略」講的是查到候選之後怎麼分級引用，沒講**一開始怎麼找到候選清單**——
沒有這一步，agent 只會用「{目的地} 必去景點」這種泛用關鍵字，撈到的是到處都在轉貼的同一批
通用排行榜，選材同質化，也是 `skill_gap_analysis.md` §6 指出的美食單一化問題的根源之一。
本節把發掘拆成兩階段，兩階段用的來源刻意不同：

### 9.1 第一階段：景點發掘 → 優先找「使用者所在國旅人」寫「目的地國」的文章

- 判定「使用者所在國」的方法同 §2.4。
- 檢索時**優先**找由使用者所在國的人、以使用者的語言，實際去過目的地國寫的遊記／部落格
  （例：使用者所在國是台灣 → 優先找台灣部落客寫的韓國遊記，而非韓國本地媒體寫給韓國人看的介紹，
  也非泛用英文遊記）。理由：這類文章天然帶著「跟使用者背景相近的人會在意什麼」的視角——
  交通怎麼從機場銜接、菜單有沒有中文、哪裡對長輩/小孩友善——比目的地國本地媒體或通用英文攻略
  更貼近使用者實際會遇到的狀況。這正是本次專案 `bobbytravel.tw`／`bigfang.tw`（皆為台灣部落客
  寫韓國遊記）已經在用的來源型態，此處是把這個隱性偏好寫成明文規則。
- 查詢方式：在使用者的語言中搜尋「{目的地/景點} 遊記／自由行／攻略」，**不限定特定網域**，
  但結果篩選時優先選「作者明顯是使用者所在國人士」的文章（語言、用詞、比較基準──例如台灣部落客
  常會換算新台幣、提到從台灣出發的班機──都是判斷依據）。
- 若使用者所在國該語言的文章數量稀少（小眾目的地常見），才降級用目的地國本地語言或通用英文來源，
  並在 `progress.md` 記一筆「該景點缺使用者所在國視角來源，改用 {實際來源語言}」。
- 這一階段找到的是**景點/區域候選**，不是美食候選——美食交給第二階段，避免整篇文章的美食推薦
  被同一位部落客的口味/踩點範圍綁死。

### 9.2 第二階段：美食發掘 → 用「目的地國當地人常用的地圖／搜尋服務」找候選 + 確保多樣性

景點定案後，**美食改查目的地國當地人自己用的地圖/搜尋服務**，而不是延用第一階段那位部落客
剛好提到的幾家店——這是確保多樣性的關鍵，同一位部落客的美食推薦通常只有 3-5 家、口味範圍窄，
當地地圖服務的候選池遠大於此。

**已實測驗證可行的方法（韓國，Naver）**：
```
curl -A "<瀏覽器 UA>" "https://search.naver.com/search.naver?query={景點或區域名}+맛집"
curl -A "<瀏覽器 UA>" "https://search.naver.com/search.naver?query={景點或區域名}+카페"
```
（WebFetch 亦可，需同樣帶瀏覽器 UA；純 domain 首頁的 WebFetch 若被擋，改用帶 UA 的 curl，
規則同 §2.5 step 1.5。）

回傳頁面內嵌一個整合式「Place」面板，會給：
- 依「많이찾는（最多人搜）／요즘뜨는（竄紅中）／TV에나온／저장많은（最多收藏）／리뷰많은（最多評論）」
  分類的候選店名——**刻意從不同分類各取 1-2 家**，不要只取排最前面那個分類，這樣選出的店才會
  在「觀光客常去」與「在地人常去」之間有真正的差異，對應 09 素材庫 `audience` 欄位
  `tourist_must`/`local_favorite` 的區分依據，而不是憑感覺標。
- 每家的 `visitorReviewScore`（評分）與評論數，可用來過濾掉評分過低或評論數過少（不夠穩定）的候選。
- 部分店家帶篩選標籤（如 `좌식`/`입식`、`휠체어출입가능`、`가족모임`、`조용한`），
  可直接填入 `party.constraints` 相關欄位的判斷依據，不必另外搜尋。

**驗證過的限制（避免踩坑）**：`map.naver.com` 的內部 API（如 `/p/api/search/allSearch`）
與 `m.place.naver.com` 的直接端點會回 403 或 429，**不要嘗試直接打這些端點**，一律走
`search.naver.com` 的整合搜尋頁面。

**重要：Place 面板本身不是可引用來源**（同 §2.5「Google 搜尋連結是補救措施不是來源」的邏輯）——
它只解決「找到候選店名」，`sources[].url` 仍要依 §1/§2 找一篇實際文章（優先同頁面內嵌的
`blog.naver.com/{user}/{postid}` 深層連結，或另外搜尋「{店名} 후기」找評測文章）並逐一開啟驗證。

**其他目的地國家**：Naver 是韓國特例，套用前必須先確認目的地國是否有等效的強勢在地搜尋/地圖生態系
（例：中國的大眾點評/百度地圖、日本的食べログ，皆與 Google 系並行甚至更主流），且要先實際試打一次
查詢確認回傳內容可用（同本節「已實測驗證」的做法），**不得假設任何國家都有 Naver 這種可用的整合面板
就直接照抄同一套 URL 模式**——沒有對應生態系的目的地，退回 §8 的通用檢索策略即可。
