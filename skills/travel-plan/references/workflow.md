# 執行模式：先自檢，再詢問

> 對應計畫書 §9 全部。

## 啟動順序（順序不可調換）

```
1. 環境能力自檢 → 寫入 progress.md「環境」欄
     網頁搜尋？檔案讀寫？子 agent？git？
     子 agent → 實測 `python3 scripts/detect_agents.py`，binary 存在 ≠ 可用（見 references/agent_routing.md）
     程式執行 → 實測 `python3 --version`（失敗再試 `python --version`），不從宿主類型推斷
     └ 無網頁搜尋 → 明確告知使用者無法執行並中止
2. 取得使用者資訊（讀既有檔案 ▸ 引導式提問 ▸ 全預設）
3. 目的地門檻檢查 → 無法辨識就輸出固定句並中止
4. 產出 trip_context.json → 請使用者確認去識別化結果
5. 【只有具備子 agent 能力時才問】要平行還是序列？
6. 建立 progress.md，開跑
```

第 5 步的位置很重要：**必須在派任何工之前**。承襲舊 orchestrator 的教訓——派工後即為非互動式，子 agent 沒機會問使用者，所有需要使用者決定的事必須在此之前一次問完。

可呼叫 agent 的偵測方式與依專長派工見 `references/agent_routing.md`；詳細的能力自檢方式與降級路徑見 `references/portability.md`；取得使用者資訊的細節見 `templates/trip_profile.template.md`；去識別化細節見 `references/privacy.md`。

## 三種模式

| 模式 | 說明 | 代價 |
|---|---|---|
| **序列**（無子 agent 時的唯一選項） | 單一 agent 逐主題執行 | 省 token；但 context 逐步膨脹，需定期清空並靠 `progress.md` 接手 |
| **平行**（具子 agent 派發能力時） | 主 agent 分波派工，同時深挖多主題 | 快；每個子 agent 各自載入 `trip_context` + 檢索規範，重複成本 ≈ 單份 × N |
| **混合**（有子 agent 時的預設推薦） | 檢索類主題平行，素材庫與行程安排序列 | 依賴結構決定的自然解，見下 |

## 依賴分析：為什麼不能全部平行

```
前置（主 agent 自己做，不需檢索）
  00 通用知識裁剪 ｜ 01 行程資訊整理

Wave 1（可完全平行，彼此不依賴）
  02 通關 ｜ 03 保險 ｜ 04 網路 ｜ 05 交通 ｜ 06 支付 ｜ 07 退稅 ｜ 08 當地習慣 ｜ 11 緊急
                            │
Wave 2（依賴 05 交通的區域可達性 + 01 的住宿區位）
  09 素材庫（景點 → 美食；美食必須等景點定了才算得出步行距離）
                            │
Wave 3（依賴 09 + 05 + trip_context 首尾時刻）
  10 行程安排（3 方案）
```

- **Wave 1** 內的 8 個主題彼此不互相依賴，具子 agent 能力時可一次全部派出，各自帶自己的 `references/sections/0X_*.md` + `references/research_rules.md`。
- **Wave 2** 的素材庫必須等 Wave 1 的 05 交通完成（需要區域可達性）才能算出景點與美食的步行距離，因此不與 Wave 1 平行。
- **Wave 3** 的行程安排需要素材庫（09）與交通（05）都完成，且需要 `trip_context.json` 的首尾時刻做 buffer 計算，是全流程最後一步。

## 跨主題呼應檢查

由主 agent 在每個 Wave 收斂時執行，平行模式下尤其重要（子 agent 各自獨立作業，容易產生不一致）：

- 推薦的交通／支付 App 是否在 04 網路、05 交通、06 支付三章之間互相呼應，沒有互相矛盾的建議。
- 10 行程安排中出現的接駁方式是否與 05 交通章節描述一致（例如末班車時間、儲值卡種類）。
- 09 素材庫列出的店家／景點是否確實被 10 行程安排實際引用，沒有素材庫收錄了卻完全沒用到的情況（若有，屬正常但應在決策紀錄簡述取捨）。
- 讀取所有子章節中的 `[待確認：...]` 標記，彙整進 `progress.md` 的「待確認清單」。

## 平行模式派工前必須問完所有需使用者決定的事

這是承襲舊 orchestrator 最重要的教訓：**子 agent 一旦被派出去就是非互動式**，沒有機會回頭問使用者任何問題。因此在啟動順序第 5 步「決定要不要平行」之後、正式派工之前，主 agent 必須：

1. 確認 `trip_context.json` 已被使用者過目確認（見 `references/privacy.md`）。
2. 確認所有「留空即預設」以外、真正需要使用者主觀決定的事項（旅行風格傾向、是否要求特定同伴友善度加權、是否有必去/必避景點）都已在引導式提問或既有資料中取得答案。
3. 對於仍不確定的事項，寧可先用預設值並在 `progress.md` 標記待覆核，也不要指望子 agent 事後能追問——子 agent 遇到必須決策的事，只能標 `[待確認]` 回報給主 agent，不能自行問使用者。
4. 派工完成、Wave 收斂後才是下一次可以與使用者互動的時機（例如 Wave 1 結束後可視情況與使用者核對交接事項）。
