# 使用者資訊取得：任意輸入 → 去識別化 JSON

> 對應計畫書 §4 全部。本檔是 `SKILL.md` 啟動流程第 2～4 步的完整規格。
> 去識別化規則與 `trip_context.json` 範例見 `references/privacy.md`；欄位型別見 `templates/trip_context.schema.json`。

## 三種取得方式（依優先序，由上往下退）

### 1. 使用者已有檔案（預設路徑）

任何 agent 讀得懂的格式都收：md、txt、訂房確認信、行事曆匯出、截圖、docx、pdf。直接讀並抽取，**不要求使用者重填表格**。

這條之所以是預設，是因為真實使用者手上通常已經有東西，而且形態混雜——常見的是同一個檔案裡同時有：半結構的行程草稿 ＋ 整段貼上的訂房確認信 ＋ 手打的班機時刻。抽取時要能容忍這種混合，不要因為格式不整齊就退回問卷。

有檔案讀寫能力時，請使用者把原始檔放進 `trips/{trip}/private/input/`（**永不進版控**，見 `references/privacy.md`）。無檔案讀寫能力時，使用者直接貼進對話即可，但仍要提醒「這段內容含個資，後續產出不會回填」。

### 2. 沒有檔案 → agent 引導式提問

**一次問一批 3~5 題，不逐題來回。** 順序：先問決定性的（目的地、日期、班機時刻、住宿區位），其餘用預設。**每題附上「不回答會怎樣」**，讓使用者能安心跳過。

可直接把 `templates/trip_profile.template.md` 的對應段落貼給偏好填表的使用者，但那是選填輔助，不是主要入口。

### 3. 什麼都不想給

除目的地外全部走預設推斷，並在 `progress.md`「待覆核的推斷值」區塊**逐項列出**。流程不中斷。

## 必須抽出的欄位與抽不到時的行為

| 欄位 | 抽不到時的行為 |
|---|---|
| **目的地** | **唯一硬停**：輸出 `SKILL.md` §1.3 的固定句並中止流程，不得續問其他事項 |
| 旅遊起訖日期 | 反問（影響季節、資訊時效、天數） |
| 出發/回程時刻與機場航廈 | 推斷該航線常見班次，標記待覆核（影響首尾 buffer，見 `references/sections/10_itinerary.md`） |
| 航空公司 | 推斷該航線主流航司，標記待覆核（影響行李規範，見 `references/sections/02_immigration.md`） |
| 住宿區位 | 推斷該目的地常見住宿區，標記待覆核（影響景點分區，見 `references/sections/09_materials.md`） |
| 成員結構 | 預設「一般成人旅客」，不做特殊加權 |
| 旅行風格、指名景點、美食偏好、預算、電信商、來源偏好 | 全部走「留空即預設」，不中斷；有明講的限制或偏好（如飲食限制）比照紅眼班機一類的例子，寫成一句 `derived_constraints`，不必另開專屬欄位 |

**所有推斷來的值都要寫進 `trip_context.json` 的 `inferred_fields`**，並同步到 `progress.md` 的「待覆核的推斷值」。使用者一旦更正，回頭改 `trip_context.json` 並記錄於「決策紀錄」。

## 草稿含多個版本時的處理（新舊版衝突）

使用者提供的檔案常常是疊代過的草稿——同一份檔案裡混雜著標題寫「old」「舊版」「作廢」的舊內容，或貼了 A/B/C 好幾種規劃卻沒說哪個算數。**一律以看起來最新的版本為準，不確定就問使用者；問不到答案也不能讓流程卡住。**

**第一步永遠是先判斷「這是不是版本衝突」**，不要看到「old」「v1」這類字樣就直接套用底下的取捨規則——草稿裡常常有一段內容跟主要行程**不是二選一關係**，只是附加資訊（例如交通方式說明、票券購買資訊、單純的备註清單），這種段落即使標題湊巧含有「舊」「草稿」等字樣，或單純出現在被判定為「舊版」的區塊之前/之後，只要它沒有在描述「同一組行程安排的另一種版本」，就不算版本衝突，照樣正常抽取，不要因為鄰近或字面相似就誤殺。判斷依據是**內容性質**（是不是在規劃同一段行程的每日/逐點安排），不是段落出現的位置或字面上有沒有「舊」字。

確認是版本衝突後，判斷優先序（由上往下，符合就停）：

1. **草稿本身有明確新舊標記**（標題含「old」「舊」「作廢」「草稿」「v1/v2」等字樣，或有一版明顯是刪除線/註記不用）→ 採用未被標記為舊/作廢的版本，其餘版本**整份排除**，不得抽取任何欄位（含 `named_musts`／`named_undecided`）進 `trip_context.json`。
2. **各版本都有日期戳記，且沒有新舊字樣**→ 採用日期最新的一版為主要版本。
3. **前兩條都判斷不出來**（無標記、無日期，或有多版時間衝突但看不出優先序）→ 這是**必問**的引導式提問之一，併入取得使用者資訊時的那一批 3~5 題，附上「不回答的話我會怎麼處理」（例如「我會採用檔案中較後出現的版本，因為通常後補寫的內容代表最新想法」）。**使用者未回覆**（無真人使用者、或逾時未答）→ 依附帶說明的預設規則自行選定，不得因此中止流程。

選定結果必須記錄，讓使用者事後看得懂發生了什麼：

- 寫進 `trip_context.json` 的 `provenance` 欄位，用使用者看得懂的白話描述選擇與理由，例如：「草稿內含 new／old 兩版行程，採用 new 版（表格式，含日期戳記）；old 版（條列式，標題明確寫 old）未採用」。這只是「用了哪一版、為什麼」的說明，不含個資，可以進版控。
- 同步在 `progress.md`「決策紀錄」補一筆，方便使用者事後回頭覆核。
- **被排除的舊版裡，若有新版完全沒提到、但看起來是具體景點/店家/活動的項目**（不是含糊的備註或已被新版取代的同類敘述），**不要只靠使用者事後自己想起來才補**——這類項目要主動列進第 3 條的那批引導式提問裡，附上清單問使用者「舊版裡的這些項目，是不是還想保留？」，跟新舊版取捨這題一起問，不必另開一輪。使用者沒回覆時，這些項目一律不納入 `named_musts`／`named_undecided`（維持排除），但要在 `provenance` 註明「舊版另有 N 項未主動確認，見 progress.md」，供使用者事後自行翻查。
- 若使用者事後表示舊版裡其實有些東西還是想要，直接把該項目視為新一輪輸入補進 `trip_context.json`，不必回頭重新跑整個判斷流程。

## 為什麼中介產物是 JSON 而不是散文

抽取結果不留在散文裡，一律整理成 `trip_context.json`：

- **下游 11 個主題都要讀它**。固定欄位不會讀歪；散文每次讀都要重新理解一次，且不同主題可能理解出不同答案。
- **去識別化檢查更可靠**：比對「有哪些欄位、值是什麼」，比在散文裡抓漏網的姓名或訂位代號穩得多。
- **與素材庫同格式**，整套 skill 只需要一條解析路徑。
- 人要看的版本另外用 md 呈現，不影響閱讀。

原始輸入（含個資）留在 `private/`，`trip_context.json` 的 `provenance` 欄位只記錄來源路徑，不複製內容。

## 產出後的人工關卡

`trip_context.json` 產出後、**第一次 commit 或第一次進入主題執行之前**，必須把去識別化結果攤給使用者過目，明確問兩件事：

1. 推斷值（`inferred_fields` 列出的）對不對？
2. 有沒有不該保留、或不該被刪掉的欄位？

這是不可跳過的人工關卡，不論當下環境是否有 git。
